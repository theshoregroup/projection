# Organizations (better-auth organization plugin)

Status: ready-for-human

Add organization support via better-auth's organization plugin with exactly one
organization — **The Shore Group** (`theshoregroup`) — and record that org on each
Project. The auth config does **not** assign users to the org (no coercion); a
one-off backfill is the only thing that does. The visible sign-in experience does
not change.

## Current state

- `packages/auth/src/auth.ts` — better-auth `1.7.0-rc.2`, Microsoft-only SSO (single
  Entra tenant, ADR 0004), **admin** plugin, drizzle adapter.
- `packages/db/src/schema/auth.ts` — generated by `pnpm cli generate` in
  `packages/auth` (user / session / account / verification).
- Migrations: drizzle-kit (`packages/db/drizzle.config.ts`, `pnpm -F @projection/db kit`),
  applied as `drizzle migrate` per the v1 plan.
- Web: `apps/web/src/lib/auth-client.ts` (client), `/login` = single
  "Continue with Microsoft" button; server session via `auth.api.getSession` in
  `packages/api/src/context.ts` and `apps/web/src/middleware/auth.ts`.

## Design decisions

| Decision | Choice | Rationale |
|---|---|---|
| Number of orgs | One — name **The Shore Group**, slug **theshoregroup** — created by the backfill | Matches the single-tenant SSO model (ADR 0004); users are company users |
| Org creation by users | `allowUserToCreateOrganization: false` | Multi-org UX is not requested; orgs exist as a container, not a feature |
| Org deletion | `disableOrganizationDeletion: true` | `member`/`invitation` FK to the org with `ON DELETE CASCADE`; deleting the one shared org would wipe every membership. `session.active_organization_id` is a plain nullable column (no FK) |
| **No coercion** | The auth config grants nothing | No auto-join on sign-in, no auto-set active org. Membership/active-org is granted **only** by the backfill script (existing users) and later the invite flow (new users) |
| Teams / dynamic access control | Off | Not needed for a single org |
| Membership | Everyone is `member`; users in `ADMIN_EMAILS` (instance admins) get the org `admin` role | Instance-wide powers still live on the admin plugin |
| `membershipLimit` | 10 000 constant | A whole-company org exceeds the default 100 |
| Org invitation emails | Not wired now | The Entra tenant is closed; per-project Pending Invites still cover sharing. `sendInvitationEmail` left unset — the deferred invite flow adds it |
| Project org | `project.organization_id` nullable FK (`ON DELETE SET NULL`) | Stamped from the Owner's `member` row at create (null when they have none), copied on duplicate. Anchor for future org-scoped features; changes no access |

**Scope boundary:** org membership changes **nothing** about Project access. Projects
remain per-user Owner/Editor grants (CONTEXT.md); the admin plugin keeps no access to
project contents. The org is recorded on each Project as the anchor for future
org-scoped features. If org-scoped project *access* is wanted, that's a separate spec.

### 1. Auth config — `packages/auth/src/auth.ts`

- Add `organization` to the `better-auth/plugins` import (order: org, admin,
  `tanstackStartCookies()` last).
- Config — shapes the plugin only, **no hooks, no coercion**:
  ```ts
  organization({
    allowUserToCreateOrganization: false,
    disableOrganizationDeletion: true,
    membershipLimit: 10_000,
    // no sendInvitationEmail, no teams, no dynamicAccessControl
  }),
  ```
- The existing `user.create.after` hook (admin role + `activatePendingInvites`) is
  untouched and no session hook is added. Org-awareness for existing users comes
  solely from the backfill (work item 3).

### 2. Auth schema + migration

- Re-run the schema generator in `packages/auth`:
  `pnpm cli generate --output ../../packages/db/src/schema/auth.ts`.
  The `1.7.0-rc.2` CLI emits the same `defineRelationsPart` (relations-v2) style as
  the checked-in file, so the diff is cleanly additive: `organization` / `member` /
  `invitation` tables, the `session.activeOrganizationId` column, and the extended
  `authRelations` block.
- `pnpm -F @projection/db kit generate` → migration `20260901115310` (three tables +
  nullable session column + indexes + FKs). All new columns are nullable, so it is
  safe to apply **before** the backfill runs.

### 3. One-off backfill script (script, not SQL — agreed)

- `packages/db/scripts/backfill-organizations.ts` — **local-only, never committed**
  (git-excluded via `.git/info/exclude`), run once, then deleted. No package.json
  script, no docs entry. Run from the repo root:
  `pnpm exec tsx packages/db/scripts/backfill-organizations.ts`.
- Idempotent, single transaction:
  1. Upsert the single org by slug (`theshoregroup`; name "The Shore Group") —
     find by slug first, create if absent.
  2. Insert `member` rows for every `user` not already a member — role `admin`
     for instance admins (`user.role === "admin"` or email in `ADMIN_EMAILS`),
     else `member`.
  3. `UPDATE session SET active_organization_id = $org WHERE active_organization_id IS NULL`
     — so *live* sessions become org-aware without a re-login.
  4. `UPDATE project SET organization_id = $org WHERE organization_id IS NULL` —
     every existing Project gets the org.
- Logs a summary (users / members / sessions / projects).

### 4. Project organization identifier

- `packages/db/src/schema/app.ts` — `project` gains `organization_id` (nullable,
  FK → `organization.id` `ON DELETE SET NULL`) + an index. Plain column, **no**
  drizzle relation: `organization` lives in the generated `authRelations` part and
  the two parts are spread into one object in `src/index.ts`.
- Migration `20260901154451` (nullable column + index + FK — safe to apply with
  existing rows).
- `packages/api` — `findUserOrganizationId(db, userId)` in `lib/access.ts` reads the
  user's `member` row (a plain read; null when they have no membership).
  `projects.create` stamps `organizationId` from it; `projects.duplicate` copies the
  source's value. Never user input.

## How the SSO sign-in migrates (answer to "migrate over as-is")

Nothing in the sign-in *flow* changes: the login page, Microsoft provider config,
single tenant, session cookies, and the `$.ts` auth route are all byte-identical,
and no hook touches org membership.

1. **Existing users** — the backfill makes them members and stamps their *live*
   sessions with `activeOrganizationId`. No re-login required; their next
   `projects.create` reads the membership and stamps the Project.
2. **Future users** — the auth config does **not** auto-join them, so they have no
   org (and `activeOrganizationId` stays null) until the deferred invitation flow
   lands. Their Projects are created with `organization_id: null` meanwhile — they
   are fully functional, just unscoped.

## Rollout order

1. Land the code: auth config, both migrations, project org identifier, client
   plugin, docs. Nothing breaks pre-backfill: every new column is nullable.
2. Apply both migrations in order (`drizzle migrate`): `20260901115310` (org tables)
   then `20260901154451` (project column) — the project FK targets the org table, so
   order matters. Deploy the app.
3. Run the backfill script once against the production DB, then delete it.
4. Verify: create a Project → it carries the org; duplicate → copy carries it; an
   org-less user (post-backfill sign-in) creates a `null`-org Project; `/admin` and
   a Board still work; existing sessions are org-aware.

## Decisions (confirmed with owner)

1. Org name **The Shore Group**, slug **theshoregroup**.
2. The backfill is a local one-off: run once, deleted before commit; no docs or
   package.json entry.
3. **No coercion** — the auth config never grants org membership or sets the active
   org; the backfill script is the only thing that does.
4. Users in `ADMIN_EMAILS` (instance admins) also get the org `admin` role.
5. `membershipLimit` is the constant 10 000.
6. Projects carry a nullable `organization_id` (the only non-auth table that does);
   `line` and `project_editor` derive it via their Project.

## Deferred work

- **Invite-based user provisioning** — the org plugin's standard invitation flow
  (`sendInvitationEmail` via trigger.dev + an accept-invitation page, matching the
  Pending Invite precedent). Since the config no longer auto-joins, this is now the
  **only** way new users enter the org — required before the org becomes a meaningful
  boundary (org-scoped features will otherwise see a shrinking population of
  org-less users/Projects as staff turnover happens).
